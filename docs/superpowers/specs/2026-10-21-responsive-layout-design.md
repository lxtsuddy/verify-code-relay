# Web 管理介面響應式版面設計規格

- 日期：2026-10-21
- 狀態：已實作（分支 responsive-layout）
- 前一份規格：`2026-10-20-web-admin-design.md`。技術選擇不變：Go `html/template` 伺服器渲染＋原生 JS，靜態檔以 `embed` 打包，不引入 Node。

## 1. 問題

在 390／1024／1100／1280／1920／2560 寬度實測（v0.2.6）：

1. **寬螢幕不變寬**：`.main { max-width: 1120px }` 且靠左，2560 寬時右側將近一半空白。
2. **1024–1280px 最差**：轉發紀錄表超出寬度，「結果」欄被切掉、需橫向捲動；主旨欄被擠成三、四行，寄件者地址在字中間斷開。這正是筆電開 125%／150% 縮放的實際 CSS 寬度。
3. **信箱清單欄位對不齊**：每列各自是一個 grid，最後的 `auto` 欄（動作按鈕）依各列內容決定寬度，所以列與列的資料夾欄起點不同；資料夾名稱與徽章被擠到換行。
4. **斷點零散且都看視窗**：640／760／860／1080／1100 分散在檔案各處，同一元件在總覽（窄）與紀錄頁（寬）無法各自調整。
5. 手機（≤640px）的卡片模式已經做得好，但切換只看視窗、而且太晚。

方案評估（框架與否）已與使用者討論：排版是 CSS 版面系統問題，前端框架解決不了；選定方案 A：保留伺服器渲染，重建 CSS 版面系統。

## 2. 目標與非目標

**目標**
- 任何寬度（320–2560px）都沒有橫向溢出：整頁不溢出，表格與清單也不需要橫向捲動。
- 寬螢幕內容**置中**於導覽列右側的區域，寬度上限依頁面類型而定（§3.1）。
- 元件依「自己拿到的寬度」排版（container queries），不再只看視窗。
- CSS 結構可維護：`@layer` 分層、統一的字級／間距設計變數、每個元件的響應式規則緊鄰元件本身。

**非目標**
- 不改配色、郵務風格元件（郵戳、郵票、郵遞區號格）、動畫。
- 不改頁面內容結構、文案、伺服器端行為、API。
- 不引入前端框架或建置步驟。
- 深色模式不在範圍內。

## 3. 設計

### 3.1 外框與頁面寬度

- `.main` 在導覽列右側的欄位中**水平置中**（`margin-inline: auto`）。
- 兩種頁面寬度（設計變數）：
  - `--page-wide: 1360px`：總覽、轉發紀錄、信箱清單、Telegram。
  - `--page-form: 1040px`：信箱新增／編輯、辨識規則、訊息範本、系統設定、版本歷史。
- 頁面以範本區塊宣告寬度：`layout.html` 的 `app` 版型以 `{{block "width" .}}wide{{end}}` 產生 `class="main main-wide|main-form"`；表單類頁面加 `{{define "width"}}form{{end}}`。不改 Go 的 `Page` 結構。
- 原本各表單自己的 `max-width`（`.mb-form` 860、`.rules-form`／`.tpl-form`／`.mailtest` 980、`.danger-zone` 860）移除，交給頁面寬度決定。
- 左右留白：`--gutter: clamp(16px, 1.2rem + 1.6vw, 48px)`；上方留白同樣以 `clamp()` 縮放。
- 頁首標題字級：`clamp(24px, 1.1rem + 0.8vw, 30px)`。

### 3.2 導覽列三段

| 視窗寬度 | 樣式 |
|---|---|
| ≥ 1200px | 現行寬導覽列（232px），目前頁面的分頁「接進」內容區 |
| 860–1199px | 精簡導覽列（約 76px）：只顯示品牌方格標誌；每個項目為圖示＋下方小字標籤（12px），目前頁面仍以「接進」造型標示；登出同樣圖示＋小字 |
| < 860px | 現行頂部列＋可橫向捲動的分頁 |

外框 `.shell` 的綠色背景寬度隨 `--rail-w` 變化。

### 3.3 斷點與 container queries

- **視窗斷點只剩三個**，只用於外框與全域元素（導覽列、留白、彈出視窗、toast）：`640px`、`860px`、`1200px`。
- **元件一律用 container queries**。容器（`container-type: inline-size`）設在：
  - `.table-wrap`（名稱 `table`）
  - `.mb-list`、`.tg-list`（名稱 `list`）
  - `.board`（總覽，名稱 `board`）
  - `.card`（名稱 `card`，用於範本編輯器、信件測試結果、Microsoft 應用程式卡片、設定列）
- 每個元件的 `@container`／`@media` 規則寫在該元件的樣式區塊內，不再集中在檔尾。

### 3.4 轉發紀錄表（總覽與紀錄頁共用）

表格保留 `<table>` 語意（grid 排版會讓部分瀏覽器丟失表格語意，所以 table／rowgroup／row／columnheader／cell 以 ARIA role 明示，`app.js` 重建的列也一樣）；`tr` 以 CSS grid 排版，所有列使用**與內容無關**的同一組欄寬，因此列與列永遠對齊。依容器寬度三種模式：

| 容器寬度 | 模式 | 版面 |
|---|---|---|
| ≥ 880px | 完整 | 時間｜信箱／資料夾｜主旨與寄件者｜種類｜（規則）｜結果，表頭顯示 |
| 600–879px | 精簡 | 第一欄上為時間、下為信箱／資料夾；中欄主旨與寄件者；末欄種類與結果上下疊放；表頭視覺隱藏 |
| < 600px | 卡片 | 現行手機卡片（時間＋結果 → 主旨 → 信箱＋種類 → 規則） |

- 主旨最多兩行（`line-clamp: 2`），完整主旨放 `title`。
- 寄件者單行、超出以「…」截斷，完整地址放 `title`；不再在字中間斷行。
- `_logs.html` 的 `log-row` 與 `app.js` 的 `recentRow()` 同步加上 `title`。

### 3.5 信箱清單與 Telegram 清單

- `.mb-list`、`.tg-list` 改為 grid，列（`li`）使用 `grid-template-columns: subgrid`，欄寬由整份清單共同決定，所以 `auto` 動作欄在每一列都一樣寬，欄位對齊。
- 依清單容器寬度：
  - 信箱清單 ≥ 900px：五欄（標誌｜帳號｜資料夾｜轉發目標｜動作）；600–899px：標誌、帳號、動作一列，資料夾與目標在帳號下方（現行 1080px 以下的排法）；< 600px：現行手機排法。
  - Telegram 清單 ≥ 720px：現行三欄／四欄；< 720px：現行手機排法。
- 資料夾名稱與狀態徽章不再被擠到換行：資料夾名稱過長時以「…」截斷，完整名稱放 `title`。

### 3.6 其他元件

- **系統狀態卡**（`.health`）：寬度判斷改用 `board` 容器，取代現在的 860／640 視窗斷點。
- **總覽信箱卡片**：維持 `auto-fill, minmax(290px, 1fr)`。
- **開始使用三步驟**：依 `board` 容器寬度決定三欄或單欄。
- **訊息範本**：編輯器與 Telegram 預覽在卡片容器 ≥ 860px 時並排（預覽 360px），否則上下排。
- **信件測試結果**：卡片容器 ≥ 760px 時細節與預覽並排。
- **Microsoft 應用程式卡片**、**設定列**（`.setting-row`）：依卡片容器寬度切換單欄。

### 3.7 驗證碼輸入（實作中使用者追加）

登入、綁定兩步驟驗證、系統設定（修改密碼、重新綁定）的驗證碼輸入改為六個獨立圓角格，外觀與其他欄位一致（白底、`--line-2` 細框、`--radius-sm` 圓角），平均撐滿欄位寬度（上限 380px）。下一個要填的格子亮綠框＋光暈並顯示游標，已填的格子邊框稍深，錯誤時轉紅並輕搖。仍是一個真正的 `<input>`（貼上、自動填入、密碼管理器照常運作），由 `app.js` 疊在格子上方並以格子顯示其值；沒有 JS 時是一個字距拉開的一般欄位。唯讀的代碼顯示（`.postcode` 紅框方格）不變。

### 3.8 CSS 結構

- 單一 `app.css`，不加建置步驟。以 `@layer tokens, base, layout, components, pages, utilities;` 分層。
- 設計變數新增：
  - 字級 `--fs-2xs` 11.5／`--fs-xs` 12.5／`--fs-sm` 13.5／`--fs-md` 14.5／`--fs-base` 15／`--fs-lg` 16／`--fs-xl` 18／`--fs-2xl` 22（px）。現有 10–11.5、12–12.5、13–13.5、14–14.5、15–15.5、17–18、20–23 分別歸入最接近的一級；郵票刻字、郵遞區號格、IP 大字、OTP 方格等裝飾性字級保留原值。
  - 間距：語意變數 `--card-pad-x`（卡片內容左右留白，20px，640px 以下 16px）與 `--section-gap`（區段上方間距，36px）。（實作時修訂：原規劃的 4px 間距尺度不採用——現有節奏 14／18／28／36px 不在 4px 尺度上，硬套會讓同一宣告混用變數與原值，或改變使用者喜歡的版面節奏。）
  - 寬度 `--page-wide`、`--page-form`、`--rail-w`、`--rail-w-compact`、`--gutter`。
- 檔頭的元件配方註解更新：寫明頁面寬度宣告方式、容器名稱與各元件的響應式模式。

## 4. 驗證

- **逐像素比對**：純整理（分層、搬移、變數化，不含字級歸併）完成後，在 640、860、1100、1280 四種寬度下，所有頁面截圖必須與修改前完全相同。
- **溢出檢查**（Playwright，所有已登入頁面＋登入／錯誤頁，寬度 390／768／1024／1100／1280／1440／1920／2560）：
  - `document.documentElement.scrollWidth <= innerWidth`；
  - 每個 `.table-wrap`、`.mb-list`、`.tg-list` 的 `scrollWidth <= clientWidth`。
- **畫面檢視**：上述寬度的總覽、紀錄、信箱、信箱編輯、Telegram、規則、範本、設定截圖，逐一人工檢視；修改前後對照給使用者。
- **總覽自動更新**：等一次 `/api/status` 輪詢，確認 JS 重建的紀錄列與伺服器渲染的列外觀一致。
- `go test -race ./...`、`go vet`、`gofmt` 全部通過。
- 截圖用的暫時測試檔（`internal/web/zz_demo_test.go`）在提交前刪除。

## 5. 相容性

container queries、subgrid、`:has()`、`@layer`、`line-clamp` 需 Chrome／Edge 117+、Safari 16+、Firefox 121+（2023 年底之後的版本）。管理介面只給單一管理員使用，可接受。
